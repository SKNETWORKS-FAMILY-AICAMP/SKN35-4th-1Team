4차 프로젝트 계획 정리

SKN35 1팀 · 3차 Docentalk 고도화 · 2026-11-03
한 줄 요약
4차는 3차 Docentalk을 이어서 발전시키는 프로젝트예요. 할 일은 Django로 백엔드 옮기기, LangGraph로 답변 흐름 정리, 하이브리드 검색으로 낮았던 점수 올리기, AWS·Docker·CI/CD로 배포하기예요. 프론트는 3차에서 배포한 Flutter Web을 그대로 써요.

주제: LLM을 연동한 내외부 문서 기반 질의응답 웹페이지 개발
필수 산출물: 요구사항 정의서, 화면설계서, LLM 연동 웹 애플리케이션, 시스템 구성도, 테스트 계획 및 결과 보고서

팀원 PDF 표시는 팀원이 정리한 「아키텍처 구조 → 보완해야 할 점」에서 가져온 내용이에요.

① 기획 · 요구사항 정의서

  • 범위: 3차 기능을 전부 가져와요(도슨트 채팅, 출처, 작품·작가·사조, 로그인, 좋아요·컬렉션, 일기, 피드·팔로우, 추천, AI 컬렉션, MCP). 옮기는 순서는 도슨트 채팅 → 카탈로그 → 로그인 → 서재·컬렉션 → 소셜 순으로 해요.
  • 기능·비기능 요구사항에 ID(FR-01, NFR-01 …)를 붙이고 우선순위를 매겨요. 3차 README의 기능 표와 PLAN.md에서 시작하면 돼요.
  • 4차에서 새로 넣는 것(LangGraph, 하이브리드 검색, AWS 배포)은 비기능 요구사항(성능·정확도·가용성)으로 정리해요.

② 화면설계서

  • 프론트는 3차 Flutter Web을 그대로 써요. 3차 운영 캡처(docs/readme-2026-10-15/)를 기반으로 정리하면 돼요.
  • 화면마다 화면 ID, 구성 요소, 동작, 연결 API를 적어요.
  • 새 화면이 생기면(예: 문서 업로드) 그 화면만 새로 그려요.

③ Django 백엔드

  • 기능별로 앱을 나눠요: accounts, catalog, chat, library, documents, llm
  • Django Ninja를 쓰면 FastAPI와 문법이 거의 같아서 api/routes/를 쉽게 옮길 수 있어요. 다른 기수도 이 방식을 썼어요.
  • SQLAlchemy 모델(models/)을 Django ORM으로, Alembic을 Django migration으로 바꿔요. 지금 TiDB 테이블을 그대로 쓰려면 inspectdb로 모델을 뽑아 오면 빨라요.
  • DB는 TiDB를 계속 써요. TiDB는 MySQL과 호환돼서 Django에서 쓸 수 있어요. 공식 백엔드 django-tidb(벡터 컬럼용 VectorField 포함)를 써요. django-tidb 6.0은 Django 6.0까지 지원하니까 Django 버전을 6.0으로 맞춰요.
  • rag/, docent/, clients/, services/는 거의 그대로 옮겨요. DB 접근만 Django ORM에 맞게 고쳐요.
  • 스트리밍 답변(SSE)은 StreamingHttpResponse로 유지해요. 이벤트 모양(token, replace, done)은 3차와 같게 둬요.
  • Django Admin으로 작품·문서를 관리하면 관리자 화면을 따로 만들지 않아도 돼요.

④ 프론트 (Flutter Web)

  • 3차에서 실제로 배포한 Flutter Web(lib/, web/, assets/, pubspec.yaml)을 그대로 가져와요. 3차의 React(src/)는 API 연결이 없는 초기 목업이라 쓰지 않아요.
  • 바꿀 것은 빌드할 때 넣는 API_BASE_URL 정도예요(scripts/write-build-defines.mjs). flutter build web 결과물(build/web)을 nginx가 서빙해요.
  • Flutter가 Firebase 로그인을 쓰니까, Django에서도 Firebase ID 토큰 검증(firebase-admin)을 3차처럼 유지해요.

⑤ 클라우드 인프라 · 배포 · 시스템 구성도

  • AWS EC2 + Docker Compose로 구성해요: nginx(HTTPS, 정적 파일) → Gunicorn/Uvicorn(Django) → TiDB · Chroma Cloud · OpenAI
  • GitHub Actions로 CI/CD를 만들어요: push하면 테스트(CI), main에 merge하면 EC2에 자동 배포(CD)
  • 비밀값은 .env.example만 커밋하고, 실제 값은 GitHub Secrets와 EC2 환경변수에 넣어요.
  • 시스템 구성도는 3차 README의 mermaid 구조도를 4차 구성(AWS, LangGraph)에 맞게 다시 그려요.

⑥ 테스트 계획 및 결과 보고서

  • 3차 평가 자료를 그대로 써요: tests/questions/*.json(45문항), scripts/eval_*.py, RAGAS 기반 LLM Judge
  • 추가할 것: Django API 테스트, 배포 환경 통합 테스트, 화면 시나리오 체크리스트
  • 보고서는 3차 기준 → 4차 개선 후 비교표로 만들어요. 이 문서의 4장 내용이 그대로 들어가요.

2. 확장 — LangGraph · 고도화

지금 상태

LangChain은 이미 쓰고 있어요(ChatOpenAI, OpenAIEmbeddings, JsonOutputParser, Document). LangGraph는 안 쓰고 있어요.
LangChain은 부품이고, LangGraph는 부품을 어떤 순서로 실행할지 정하는 설계도예요.

지금은 docent/service.py의 answer() 안에 if문으로 흐름이 짜여 있어요.

질문 → 분류 → 거절? → 바로 답변? → 범위 밖? → 추천? → 검색 → 자료 없음? → LLM 생성 → 검증 → 답변

팀원 PDF 게다가 같은 흐름이 두 곳에 따로 구현돼 있어요. docent_service.answer(일반 답변)와 docent_stream.answer_events(스트리밍)가 분류·범위 판정·검색·생성·검증을 각각 해요. 스트리밍 쪽은 RAG가 아닌 질문을 처리할 때 answer()를 다시 불러서 분류를 한 번 더 해요. 그래서 한쪽만 고치면 두 경로의 동작이 달라져요.
→ LangGraph로 그래프 하나를 만들고, 일반 답변과 스트리밍이 같은 그래프를 쓰게 하면 이 문제가 구조적으로 해결돼요. LangGraph를 써야 하는 가장 분명한 이유예요.

① 기본: 지금 흐름을 그래프로 옮기기

[분류] ─거절──→ [거절 답변] ─→ 끝
   ├──바로 답변→ [카탈로그 답변] ─→ 끝
   ├──추천────→ [추천] ─→ 끝
   └──RAG────→ [검색] → [생성] → [검증] ─→ 끝
  • 지금 있는 classify, retrieve, generate, validate_response를 노드로 감싸기만 하면 돼요. 새로 짜는 로직은 거의 없어요.
  • 흐름도 그림이 자동으로 나와서 시스템 구성도와 발표 자료에 바로 쓸 수 있어요.
  • 스트리밍은 LangGraph의 stream_mode="messages"로 생성 노드의 토큰을 받아요. 그래서 흐름을 한 번만 짜면 돼요.

② 고도화: "근거가 부족하면 다시 찾기" 루프

[검색] → [근거 판정] ─부족→ [질문 다시 쓰기(LLM)] → [검색]   (최대 2회)
                     ├─충분→ [생성]
                     └─2회 후에도 부족→ [거절(NO_EVIDENCE)]  ← LLM 호출 없이
  • 팀원 PDF 지금 후속 질문 처리는 "그 사람", "아까" 같은 말을 정규식으로 찾아서 직전 질문을 앞에 붙이는 방식이에요. 이걸 LLM으로 질문을 다시 쓰는 노드로 바꿔요.
  • 팀원 PDF 관련도 기준선: 지금은 거리가 아무리 멀어도 검색 결과가 항상 LLM에 들어가요. 근거 판정 노드에서 점수가 기준 미만이면 LLM을 부르지 않고 바로 거절해요. 기준값은 기존 평가 세트에서 정답이 있는 질문과 거절해야 하는 질문의 점수 분포를 비교해서 정해요.

③ 확장: 대화 기억 (checkpointer)

  • LangGraph checkpointer로 이전 대화 맥락을 이어받아요. 지금 DB에 저장하는 대화 기록과 연결해요.
  • 지금은 "최근 6턴 × 600자"처럼 글자 수로 자르는데, 이걸 토큰 기준으로 바꾸는 작업과 같이 하면 좋아요(3장 참고).

하이브리드 RAG 설계 팀원 PDF

팀원이 제안한 A안이에요. 지금 데이터 규모에 가장 단순하고 빨라요.

  1. 작품별 청크를 메모리 캐시에 두기: 작품별로 범위 안 청크의 본문과 벡터를 한 번 불러와 TTL 캐시에 둬요(키: artwork_id). sync_chroma나 build_chunks를 돌리면 캐시를 비워요.
    → Chroma query()/get() 왕복이 0회가 되고, 필터 검색에서 청크가 빠지는 문제가 사라져요. 남는 외부 호출은 질문 임베딩 1회뿐이에요.
  2. 한국어 BM25: kiwipiepy 형태소 분석으로 명사·고유명사·숫자만 색인하고, rank_bm25를 써요. 작가 별칭(artist_aliases.jsonl)을 사용자 사전에 넣어서 "렘브란트 판 레인" 같은 이름이 쪼개지지 않게 해요.
    → 연도(1642), 작품명(『야경』), 기법명(테네브리즘) 같은 질문이 좋아져요.
  3. RRF로 합치기: 점수 = 1/(60+벡터순위) + 1/(60+BM25순위). 두 점수의 단위를 맞출 필요가 없어서 튜닝이 쉬워요. 지금의 자리 보장 규칙(MAX_PER_DOC, OWN_K, 연표·보정문 고정)은 RRF 뒤에 그대로 적용해요.
  4. 리랭커는 선택: RRF 상위 15~20개만 리랭크해서 5~8개로 줄여요. Cohere rerank-multilingual(API, 수백 ms)이나 bge-reranker-v2-m3(직접 호스팅, CPU·메모리 부담 큼) 중에서 골라요. 1~3번을 먼저 적용해서 평가해 보고, 점수가 부족할 때만 추가해요.
  5. 관련도 기준선으로 일찍 거절: 최상위 점수가 기준 미만이면 NO_EVIDENCE_MESSAGE로 바로 거절해요.
  6. 대안: 문서가 크게 늘면 TiDB 전문 검색(FULLTEXT) + 벡터 검색, 또는 Chroma Cloud sparse 벡터로 옮길 수 있어요. 지금 규모에서는 1번이 더 빠르고 단순해요.

4. 테스트 기준 미달 항목과 해결 방법

❌ ① refused 값 정합성 6/8 (75%)

  • 무슨 문제냐면: 답변 본문에는 "이 자료로는 확인할 수 없어요"라고 쓰고, 거절 여부 값은 refused=false로 보낸 경우예요. 내용이 틀린 게 아니라 표시가 틀린 거예요.
  • 원인: docent/grounding.py에서 LLM이 refused 값을 직접 정하는데, 가끔 본문과 값이 엇갈려요.
  • 해결 (쉬운 순서)
    1. 서버에서 한 번 더 확인: 출처(used_document_ids)가 하나도 없거나 답변에 "확인할 수 없", "자료에 없" 같은 표현이 있으면 서버가 refused=true로 고쳐요. 코드 몇 줄이면 돼요.
    2. 프롬프트 보강: "확인 불가를 설명할 때는 반드시 refused=true" 규칙과 예시를 넣어요.
    3. LangGraph의 [검증] 노드에 1번 로직을 넣어요.
  • 가장 빨리 고칠 수 있어요. 보고서에 "75% → 100%"로 바로 쓸 수 있어요.
